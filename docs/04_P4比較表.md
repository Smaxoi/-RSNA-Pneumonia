## 0. 怎麼更新這份表（不用手打）

1. 把群組裡所有回報行複製到 `reports/回報行.txt`（一行一筆，中間夾雜聊天內容沒關係）
2. 跑：

```powershell
python src/collect_reports.py reports/回報行.txt
```

3. 它會印出 Markdown 表格，連 checksum 核對和 ±0.02 判定都算好，直接貼回下面第 2、3 節

> `reports/*.txt` 已經在 `.gitignore` 裡，所以那份貼滿群組訊息的原始檔不會被推上公開 repo。
> 要進 git 的只有整理好的表格，也就是這份文件。

程式會自動做三件人工容易漏掉的事：

- **核對 checksum** —— 不一致就直接標紅，因為那代表 val split 不同、數字不能比
- **算全距** —— 超過 ±0.02 才叫「有差異」
- **擋掉不能相減的比較** —— 一邊是 `best`、一邊只有固定門檻時不給差距，避免算出假的進步

### 這張表現在能講的結論

**四個設定的全距只有 0.008，全部落在 ±0.02 容許誤差內。**

所以正確的說法是：

> 「在 10 epoch、yolov8n 的條件下，影像尺寸 512→640 和關掉 mosaic
> **都沒有造成可量測的差異**。」

**不可以說**「640 比 512 差」。差 0.008 是雜訊，說它是結論就是過度解讀 ——
這點講出來反而是加分的，表示我們知道自己的誤差範圍。

要讓這兩個變因分得出高下，需要其中一項：
延長訓練（`EPOCHS` 10 → 30）、擴大資料（`SUBSET_PATIENTS` 8000 → 全部），
或同設定重跑三次取平均。時間允許的話優先做第一項。

## 4. 已經站得住腳的一個實證結論

**`BOX_SHRINK` 在這個訓練長度下不該縮。**

掃描結果裡 `shrink=1.0`（完全不縮）在多數情況贏過 `0.90` 和 `0.85`，
**這跟社群常見的「縮框能提分」相反。**

為什麼合理：縮框的前提是「框位置已經抓對，只是畫太大」。
但只訓練 10 epoch 的模型框本身就不準，把一個歪的框縮小，只會讓它跟真實位置差更多。

這一條比照抄別人的經驗值有說服力，**適合放在 P4 或 P1 當論點**。

## 5. 欄位的意思（上台前要知道自己在念什麼）

| 欄位 | 意思 | 為什麼需要它 |
|---|---|---|
| **固定門檻 mAP** | 大家都用 `conf=0.10` 算出來的分數 | 五個人唯一完全可比的數字 |
| **best mAP** | 掃過所有門檻和縮放後的最佳值 | **這才是這個變因真正的成績** |
| **最佳 conf / shrink** | best 是在哪個組合拿到的 | 不同設定的最佳門檻會飄，必須一起記 |
| **maxconf** | 模型給出的最高信心 | 判斷門檻訂得合不合理的唯一依據 |
| **checksum** | val patientId 排序後的 md5 前 12 碼 | 不一致 = val split 不同 = 整張表作廢 |

### 三個陷阱

1. **不要拿 `best` 跟別人的固定門檻 mAP 比。** 那是兩種東西，差距全是假的。
2. **差距 ≤ 0.02 不叫差異。** GPU 非確定性本來就有這個幅度。
3. **checksum 不一致就先停下來。** 修好再重跑，不然後面所有分析都白做。
